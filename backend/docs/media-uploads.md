# Media uploads

Media files are prepared in the browser before the existing multipart and authenticated resumable-upload paths send them to Laravel. The shared preparer is used by `postJSON`/`sendMediaFormData`, the direct chunk-upload helper, and explicit admin/event/legacy migration preparation. It selects an image profile from the multipart field name (or an explicit profile for chunked callers); images become WebP, which supports alpha transparency, while the browser applies image orientation and removes EXIF metadata. Compression tries gradually lower quality at the profile's maximum dimension, then reduces dimensions in controlled steps. Size values are targets, not guarantees: if every attempt remains over target, the smallest valid result is retained; an already supported original is retained when it is suitable and smaller than a recompressed output. Corrupt or undecodable input fails before upload. Actual decoding and WebP support depend on the user's browser.

| Image use | Target size (approx.) | Maximum dimension | Starting WebP quality |
| --- | ---: | ---: | ---: |
| Resort galleries and event galleries | 150–350 KB | 1600 px | 82 |
| Covers, banners, and generic primary images | 250–500 KB | 1920 px | 85 |
| Enterprise logos | 30–150 KB | 1000 px | 82 |
| Profiles, avatars, receipts, and thumbnails | 30–100 KB | 800 px | 78 |

Gallery-like fields such as `images[]` use the gallery profile; `logo` uses the enterprise-logo profile; avatar/profile/thumbnail/receipt fields use the thumbnail profile; and `image`, cover, banner, and background fields use the cover profile. This keeps resort owner, enterprise, admin, profile, accommodation, event, landmark, and other existing multipart endpoints on their existing routes while applying preparation before transmission. Server-side `ValidateApiRequest` verifies uploaded-file validity, detected signature MIME, matching extension, per-file size, and aggregate image limits; endpoint-specific Laravel rules remain in force. WebP is accepted by the shared signature/extension validator and the image-bearing controllers inspected. Laravel stores the prepared bytes on the existing public disk and persists paths/metadata rather than Base64 content.

Videos are processed only when selected, using one lazily loaded FFmpeg.wasm worker at a time. The browser emits MP4/H.264/AAC, caps output resolution at 1920×1080 without upscaling, uses a `veryfast` preset and CRF 27, and uploads no original if processing fails. The default browser input limit is 200 MiB and duration limit is 600 seconds; configure them at frontend build time with `VITE_VIDEO_PROCESS_MAX_INPUT_MB` and `VITE_VIDEO_PROCESS_MAX_DURATION_SECONDS`. FFmpeg.wasm uses browser memory for input and output, so increase these only after testing target devices. Oversized or unsupported videos produce an error instead of falling back to the original. The image worker and FFmpeg core are served from the built frontend; no media is sent to a third-party processing service.

Compression, validation, previews, and transfer progress are integrated with existing multipart forms and the authenticated resumable uploader. The event gallery and admin homepage video use authenticated 4 MiB chunks; admin content publishing now also uploads prepared images and videos through that chunk API, then sends a small JSON request containing the returned storage paths. The controllers verify ownership, MIME type, image count, and the combined 50 MiB staged-image limit before saving the content record. Other existing forms continue to call their existing Laravel endpoints. Laravel does not resize, recompress, or transcode uploaded media. It validates file signatures, filename extensions, image count/combined size, per-file limits, authorization, and ownership, then saves the processed file to the existing local public disk. Chunked media is assigned a server-generated UUID filename, staged privately under `storage/app/media-uploads`, and finalized under `storage/app/public/originals/{userId}`. Existing controller uploads continue using their existing public-disk directories and generated filenames.

## Limits and frontend configuration

| Setting | Default | Meaning |
| --- | ---: | --- |
| Combined compressed images | 50 MiB | Exact `50 × 1024 × 1024` byte ceiling per multipart submission or event-gallery submission. |
| Images per request | 20 | Maximum uploaded image files in one API submission. Existing event galleries remain limited to 10. |
| `UPLOAD_MAX_IMAGE_SIZE_MB` | `50` | Per-image server cap, bounded to 1–50 MiB; the combined image cap still applies. |
| `UPLOAD_MAX_VIDEO_SIZE_MB` | `2048` | Server per-video cap, bounded to 1–4096 MiB. |
| `UPLOAD_USER_QUOTA_GB` | `10` | Per-user quota for the chunked uploader, including active staging data. |
| `UPLOAD_INCOMPLETE_EXPIRY_HOURS` | `24` | Age after which unfinished upload sessions are removed. |
| `UPLOAD_ORPHAN_CLEANUP_GRACE_HOURS` | `168` | Minimum age before a failed operation's unreferenced, completed upload is retried for cleanup. |
| `UPLOAD_FINALIZE_TIMEOUT_SECONDS` | `3600` | Maximum PHP execution time for streaming and validating a completed chunked upload. |
| `VITE_VIDEO_PROCESS_MAX_INPUT_MB` | `200` | Maximum video size the browser will attempt to transcode. |
| `VITE_VIDEO_PROCESS_MAX_DURATION_SECONDS` | `600` | Maximum source-video duration accepted by the browser transcoder. |

Image total-size checks are applied again to every direct multipart API request by `ValidateApiRequest`; they count server-detected image files, not videos. The frontend keeps image bytes at or below 49 MiB to leave room for multipart overhead, while Laravel enforces the exact 50 MiB image total. Event-gallery submissions also re-check the total sizes of staged image paths owned by the submitting account. The chunk API limits image size per file; gallery references are checked again before an event is saved. Images have both a 50 MiB per-file ceiling and a 50 MiB combined submission ceiling.

## Storage, authorization, and deployment

The application uses Laravel's existing `public` disk (`storage/app/public`) and `/storage/...` URLs. Keep the existing `php artisan storage:link` arrangement and web-server permissions. Chunk staging is private to the Laravel local disk and isolated by authenticated user ID. After a validated permanent file is stored, Laravel writes a `media_assets` row containing its upload ID, owner, operation key, storage path, detected MIME type, byte size, SHA-256 checksum, and timestamps. Content records continue to store media paths and their existing descriptive fields; binary contents and Base64 payloads are never stored in the database.

The chunk routes remain behind JWT authentication and role authorization for admin, enterprise, and resort accounts. Direct form routes retain their existing middleware, including the existing authentication and ownership checks. Validation uses PHP `fileinfo` rather than trusting browser-supplied MIME values, and filename extensions must match the detected content.

The checked-in Apache Docker configuration sets `LimitRequestBody 2306867200` bytes (2,200 MiB) and `Timeout 3600`. Its PHP configuration sets `upload_max_filesize=2048M`, `post_max_size=2100M`, `max_execution_time=300`, and `max_input_time=3600`; thus PHP's multipart-body limit is the tighter bound for a direct upload of a 2 GiB file plus multipart fields. The resumable client sends chunks of up to 4 MiB as raw binary and the Laravel endpoint rejects larger chunks; allow at least 5 MiB at any upstream proxy for chunk requests and protocol overhead. Direct multipart request limits must also allow the configured file size plus multipart fields; the checked-in PHP/Apache values are intended to support the existing 2 GiB direct-video ceiling. The Docker Apache configuration does not establish what is configured on the live Apache host or any proxy in front of it. No live virtual-host or upstream-proxy configuration was available for inspection, so the production HTTP 413 limit and timeout remain unverified. Do not apply Nginx settings unless the actual upstream is confirmed to be Nginx. The frontend host must serve its generated FFmpeg `.wasm` asset and worker from the same origin and permit WebAssembly execution under its content-security policy.

Run Laravel's scheduler (`php artisan schedule:run` every minute) so `media:clean-incomplete-uploads` removes expired staging directories and `media:cleanup-orphaned-uploads` retries cleanup of old, unreferenced files from failed content saves. The orphan reconciler processes operation-key upload manifests and locally queued cleanup markers for direct accommodation uploads, waits for the configured grace period, checks known content tables before deleting, and retains files if a reference check fails. Local staging and final media require adequate disk space; horizontally scaled instances need shared local storage or a separately designed storage driver. No S3 or external object storage is used.

Legacy `discover-mansalay:custom_resorts` data is never deleted by the frontend migration. Admins must download the versioned JSON backup before starting migration. Media is prepared with the browser pipeline, uploaded to the authenticated chunk endpoint, and only then linked by the idempotent `legacy_resort_migrations` database record. The original key remains available as a recovery source; export the backup again if a browser cache or device is at risk. Completed migrations can be retried safely using the same stable migration key.

For CI/deployment builds, use a memory-rich Node runner (at least 4 GiB available is recommended for this Vite application), run `npm --prefix frontend ci` and `npm --prefix frontend run build`, then deploy the generated `frontend/dist` output to the configured frontend document root. The repository's `backend/Procfile` starts Laravel with `php artisan serve --host=0.0.0.0 --port=$PORT`; the root `npm start` serves `frontend/dist` on `$PORT`. No Render service configuration, live proxy request limit, frontend document-root mapping, or service/container name is checked in, so the platform-specific publish/restart command cannot be inferred. The checked-in Apache include sets `LimitRequestBody` and `Timeout 3600`; it does not set `ProxyTimeout`, which should only be configured if an Apache proxy is actually present. PHP `max_input_time` is 3600 seconds and `max_execution_time` is 300 seconds, while the resumable finalization service has its own Laravel timeout configuration. Verify the actual Apache/proxy read and execution timeouts for the selected deployment; do not assume the Docker image values are live values. The proxy in front of either deployment must allow at least 5 MiB for chunk requests; direct multipart limits must match the endpoints actually used.

The backend image can be built from the repository root with `docker build -f backend/Dockerfile -t discover-mansalay-backend:latest .`. Deploy that image through the existing host runtime, then run `php artisan migrate --force` and ensure Laravel's scheduler is configured as described above. For a Procfile-based deployment, the exact application start command is `php artisan serve --host=0.0.0.0 --port=$PORT`; run `php artisan schedule:run` every minute through the platform scheduler. The frontend is not included in the Docker image; publish `frontend/dist` separately (or start the checked-in root Node server with `npm start`). A restart/deploy command still depends on the external service name and is intentionally not guessed.
